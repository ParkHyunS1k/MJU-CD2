# 프로젝트: 인바디 기반 대사질환 위험도 예측 + 식단·생활습관 리포트 앱 (캡스톤)

## 개요
- 4인 팀, 12주, Android + iOS 앱 + 백엔드
- 흐름: 인바디 결과지 이미지(종이 사진, 앱 캡처. PDF는 제외) → 수치 추출 → 검증 → 사용자 확인 → 위험도 예측 → 식단 생성 + 생활습관 리포트

## 포지셔닝 (반드시 지킬 것)
- "진단" 금지. "대사질환 위험도 예측 / 건강관리 참고"로 표기 (비의료건강관리서비스 취지)
- 금지 표현: 진단, 치료, 처방. 인과 주장 금지 ("이렇게 하면 위험도 N% 감소" 불가)
- 이용 대상에서 임산부, 미성년 제외. 극단적 저열량 식단 방지(열량 하한)

## 차별점 = 검증 가능성
- 경쟁: 재다(Body X8, 체성분 + 대사증후군 위험도 + 식단 코칭)가 가장 근접. WYT, OneFit은 인바디 OCR 자동입력을 이미 제공 → OCR 자체는 차별점이 아님
- 차별화 지점: 공개 데이터로 학습·평가, BMI baseline 대비 성능 공개, 불확실성과 "판단 보류", 성별·연령 하위집단 성능, 영양값은 DB로 계산 + 제약 충족률 공개, 하드웨어 비종속

## 데이터
- 위험도 모델: KNHANES(질병관리청, 일부 주기 DXA 체성분 포함), 건보공단 건강검진 개방데이터 (컬럼과 이용약관은 직접 확인 필요)
- 라벨: 대사증후군 기준(허리둘레, 혈압, 혈당, 중성지방, HDL 중 3개 이상). 허리둘레를 입력 변수로 쓰면 라벨 누수이므로 주의
- 알려진 한계: 학습 데이터(DXA/줄자)와 실제 인바디(BIA) 측정 방식이 달라 도메인 갭 존재. 혈액 라벨이 없어 외부 검증 불가. 발표에서 한계로 명시
- 식단: 식약처 식품영양성분 DB + 한국인 영양소 섭취기준(KDRIs). LLM이 영양 수치를 말하지 않고 DB 조회로 계산

## 입력 추출(OCR) 방침
- 추출은 전부 온디바이스(iOS·Android). LLM 미사용. 이미지는 기기 밖으로 나가지 않고, 사용자가 확인한 숫자만 서버로 전송 (2026-10-12 결정, 서버 LLM 경로 폐기)
- 흐름: 촬영 → ML Kit 텍스트 인식(한국어) → 규칙 파서 → 검증 → 사용자 확인 → 숫자 전송. 서버도 같은 검증을 한 번 더 수행
- 파서·검증은 Python 프로토타입(ocr/)으로 먼저 만들고 tests/vectors 공용 테스트 벡터로 Dart/TS 포팅본을 검증. 개발 중 OCR은 Mac Apple Vision으로 대체하되 최종 평가는 실기기 ML Kit 출력으로
- 검증 레이어(필수): 범위 검사, 체중 ≈ 체수분 + 단백질 + 무기질 + 체지방량, BMI = 체중/신장², 체지방률 = 체지방량/체중. 실패 필드는 저신뢰로 표시해 사용자 확인
- 평가: 입력 유형(사진/캡처)별 필드 단위 exact match, 핵심 지표는 "틀렸는데 검증을 통과한 비율"

## 모델·평가 계획
- 위험도: 로지스틱 회귀 baseline vs LightGBM/XGBoost, 확률 보정(isotonic/Platt), SHAP, 분포 이탈 탐지로 판단 보류
- 지표: AUC, 특이도 고정 시 민감도, calibration, BMI-only baseline 대비 개선, 하위집단 AUC, 생활습관 변수 추가 시 AUC 변화
- 식단: 영양 제약 충족률, 수치 환각률(LLM 값 vs DB 값), 알레르기·금지표현 위반율

## 개인정보·보안 규칙
- 인바디 이미지는 서버로 보내지 않는다(온디바이스 처리). 촬영·처리 안내/동의 화면 필수. 이름 영역은 가리고 촬영하도록 안내
- API 키, .env는 커밋 금지. 키는 서버에만 둔다 (앱에 넣지 않음)
- 샘플 검사지 이미지는 Git에 올리지 않는다 (비공개 드라이브)
- 원시 공공데이터는 재배포 제한 확인 후 Git 제외

## 팀·환경 제약
- Mac + iPhone 사용자 1명(iOS 빌드 담당), Flutter/Dart 경험자 없음. 앱은 React Native(Expo, mobile/). ML Kit 같은 네이티브 모듈은 Expo Go에서 안 돌아가므로 development build 필요
- OCR 테스트는 실기기에서. 백엔드는 FastAPI 후보, 중반에 저가 클라우드 배포

## 범위 밖 (향후 과제)
자세교정(CV, 포화 시장), 복약 상호작용(DUR 영역), 근감소증 스크리닝, what-if 시뮬레이터

## 작업 원칙
- 경쟁 서비스나 데이터셋 사양처럼 확인되지 않은 사실은 단정하지 말고 "미확인"으로 표시하고 검증 방법을 제시
- 기능을 늘리기보다 핵심 + 3~4개로 스코프 유지
