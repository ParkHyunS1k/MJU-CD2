# 영양제 후보 근거: 식약처 건강기능식품 기능성 원료

## 왜

리포트의 영양제 칸이 거의 항상 비어 있다(2026-11-23 KNHANES 5명 미리보기에서 5명 모두 0개). 영양제 후보는
`supplement` 분류 조각만 근거로 쓸 수 있는데(`citation_service.validate_citations`), 그 분류의 문서는 질병관리청
포털 "영양제"·"건강기능식품" 두 개뿐이고 대부분 "골고루 먹으면 충분하다", "구매 요령" 같은 일반 안내다. 영양제 쿼리도
모든 사람에게 같은 문장 하나(`SUPPLEMENT_QUERY`)라 원료 이름이 있는 근거가 프롬프트에 들어가지 않는다.
사용자는 위험 질환에 맞는 원료가 근거와 함께 나오기를 원한다(옵션 B, 사용자 결정).

## 목표 / 비목표 / 반목표

- 목표
  1. 식약처가 기능성을 인정한 원료(고시형 + 개별인정형, 사용자 결정) 중 앱 질환과 관련된 것을 영양제 근거로 쓴다.
  2. 위험도가 medium 이상인 질환과 체성분 유형에 맞는 원료만 골라 프롬프트 근거로 넣는다. 벡터 검색은 쓰지 않는다
     (사용자 결정: 방식 B).
  3. 리포트가 인용하면 출처에 식약처와 원료 인정 정보가 표시된다.
- 비목표: 프론트 화면 수정, 위험 모델 수정, 영양제 외 근거 검색 방식 변경, 관절·눈·피부 등 앱 질환과 무관한 기능성.
- 반목표(돌아가도 실패)
  - 근거 없는 원료가 후보로 나오는 것(지금 인용 검증 규칙이 그대로 막아야 한다).
  - 같은 사람·같은 기록인데 프롬프트에 넣는 영양제 근거 목록이 실행마다 달라지는 것. 그 안에서 리포트에 실을 후보
    (최대 3개)는 GPT가 고르므로 리포트를 다시 만들면 바뀔 수 있다. 이것은 받아들인다(사용자 결정 (가)).
  - 영양제 근거가 진료지침·포털 근거 자리를 밀어내는 것.
  - 치료·개선 보장처럼 읽히는 표현. 진료지침 우선, "보조 후보" 규칙은 지금 그대로.
  - 식약처 데이터 수집 실패 때문에 리포트 생성이 실패하는 것(런타임은 저장된 파일만 읽는다).

## 데이터

- 출처: 식품안전나라 OpenAPI. 키는 루트 `.env`의 `FOODSAFETYKOREA_API_KEY`(이미 있음, 활용신청 완료 확인).
  - `I2710` 건강기능식품 품목분류정보(555건, 2026-11-18 갱신). 고시형과 개별인정형이 함께 있다.
    필드: `PRDCT_NM`(원료명), `PRIMARY_FNCLTY`(주된 기능성), `DAY_INTK_LOWLIMIT`/`DAY_INTK_HIGHLIMIT`/`INTK_UNIT`,
    `INTK_MEMO`, `IFTKN_ATNT_MATR_CN`(섭취 시 주의사항), `LAST_UPDT_DTM`.
    개별인정형은 원료명에 인정번호가 붙어 있다(예: `Nopal 추출물(제2009-39호)`). 번호가 없으면 고시형으로 본다.
  - `I-0050` 개별인정형 정보(457건). 관련 원료 143개 중 140개는 `I2710`에 같은 인정번호로 있다.
    `I2710`에 없는 인정번호의 원료만 더한다. 필드: `RAWMTRL_NM`, `PRIMARY_FNCLTY`, `HF_FNCLTY_MTRAL_RCOGN_NO`,
    `DAY_INTK_LOWLIMIT`/`DAY_INTK_HIGHLIMIT`(문자열에 단위 포함), `IFTKN_ATNT_MATR_CN`.
  - 응답은 `{서비스명: {total_count, row: [...], RESULT}}`, 한 번에 최대 1,000건(`/json/1/1000`).
- 거르기: `PRIMARY_FNCLTY`로 아래 기능성 태그를 단다. 태그가 하나도 없는 원료는 버린다(예상 약 180개 남음).

| 태그 | 기능성 문구 예 | 쓰는 곳 |
|---|---|---|
| `blood_glucose` | 혈당, 식후 혈당 상승 억제 | 질환 `diabetes` |
| `blood_pressure` | 혈압 | 질환 `hypertension` |
| `cholesterol` | 콜레스테롤 | 질환 `cholesterol` |
| `triglyceride` | 중성지방, 중성지질 | 질환 `triglyceride` |
| `body_fat` | 체지방 감소 | 체성분 유형 `지방 감량형`, `지방→근육형` |
| `muscle` | 근력, 근육량 | 체성분 유형 `근육 보강형`, `지방→근육형` |

  `muscle`은 "근육"만으로 잡으면 칼슘·마그네슘("근육과 신경 기능 유지에 필요")처럼 근력과 무관한 영양소 기능성이
  걸린다. 태그 규칙은 빌더가 정하되, 이런 오태깅을 테스트로 막는다.
- 저장: 거른 결과를 저장소의 JSON 파일 하나로 둔다(위치·이름은 빌더). 서버는 이 파일만 읽는다. DB 테이블·임베딩은
  쓰지 않는다. 공공데이터라 커밋해도 된다. 원료마다: 원료명, 고시형 여부, 인정번호(있으면), 주된 기능성, 1일 섭취량
  (하한·상한·단위·메모), 섭취 시 주의사항, 태그, 원본 갱신일.
- 갱신: 수집 스크립트(예: `python -m rag.mfds`)를 다시 돌려 파일을 새로 만든다. 받은 건수가 비정상(0건 또는 관련
  원료가 크게 줄어듦)이면 파일을 덮어쓰지 않고 멈춘다(`rag/load.py`의 `IncompleteIngest`와 같은 취지).

## 고르기 (사용자 결정: ① 고시형 먼저, 태그당 최대 5개)

- 필요한 태그: 위험도 `risk_level`이 medium·high인 질환의 태그 + `personal_metrics.body_type`의 태그.
  둘 다 없으면 영양제 근거를 넣지 않는다(모든 위험이 낮은 사람은 영양제 칸이 비는 것이 정상).
- `body_type`이 `근육 판정 불가`여도 `fat_excess`가 참이면 `body_fat` 태그를 단다. 체지방 과다는 근육 판정과 따로
  측정된 사실이기 때문이다. 근육 태그는 달지 않는다. 프롬프트의 "근육 판정 불가면 유형을 언급하지 마세요" 규칙은
  그대로다(유형 이름을 말하지 않고 체지방률로 설명). — 내 판단: 실제 기록 9개 중 근육조절이 있는 것은 4개뿐이다.
- 태그마다 최대 5개: 고시형을 먼저, 그다음 개별인정형. 같은 그룹 안의 순서는 파일에 저장된 순서(수집 시 원본 순서
  유지)로 고정한다. — 내 판단: 사람·기록이 같으면 결과가 같아야 한다(반목표).
- 같은 원료가 여러 태그에 걸리면 한 번만 넣는다.
- 영양제 근거 전체 상한은 10개. 태그가 많으면 태그별 1위부터 돌아가며 고른다(지금 `select_evidence`의 라운드 로빈과
  같은 방식). — 내 판단: 태그 4개 × 5 = 20개를 다 넣으면 프롬프트가 영양제로 차고 진료지침 근거가 묻힌다.
- 이 근거는 기존 `MAX_EVIDENCE = 15`와 별도로 더한다. 기존 검색 결과를 하나도 빼지 않는다(반목표). — 내 판단
- 기존 `SUPPLEMENT_QUERY`(포털 영양제 문서 검색)는 그대로 둔다. 일반 주의사항 근거로 계속 쓴다.

## 프롬프트·인용

- 고른 원료는 기존 `Evidence`와 같은 모양으로 만든다: 이어지는 S번호, `chunk_category = "supplement"`,
  본문은 원료명·주된 기능성·1일 섭취량·주의사항을 담은 짧은 문장. 지금 인용 검증(영양제는 `supplement` 근거만)과
  출처 표시가 그대로 동작해야 한다.
- 출처 표시: 제목은 원료명(인정번호 뺀 이름), 발행처 "식품의약품안전처", 소제목에 "고시형" 또는
  "개별인정형 제XXXX-XX호", 연도는 원본 갱신일의 연도. 링크는 식품안전나라 원료 페이지가 있으면 그것, 없으면 없음.
  `Evidence`의 `chunk_id`·`document_id`는 DB 조각이 아니므로, DB 조각과 겹치지 않는 값으로 둔다(빌더).
- 프롬프트 규칙 추가(문구는 빌더):
  - 영양제 후보의 `name`은 근거에 적힌 원료명(인정번호를 뺀 이름)을 그대로 쓴다. 지어낸 일반명으로 바꾸지 않는다.
    개별인정형 원료명에 붙은 회사·제품 표시는 사용자가 개별인정형을 넣기로 하며 받아들인 것으로 보고 그대로 둔다. — 내 판단
  - `cautions`·`not_recommended_if`는 근거의 섭취 시 주의사항에서 가져온다.
  - 기능성 문구는 "~에 도움을 줄 수 있음" 수준을 넘지 않는다.
- 인용 검증 강화: 영양제 후보는 식약처 원료 근거를 하나 이상 인용해야 남는다. 포털 "영양제"·"건강기능식품" 문서는
  주의사항 근거로 함께 인용할 수는 있지만, 포털 문서만 인용한 후보는 뺀다. 지금은 `supplement` 분류 근거면 무엇이든
  통과하므로 포털 문서 속 원료나 지어낸 원료가 통과할 수 있다. 후보 `name`과 원료명의 글자 일치 검사는 하지 않는다
  (표기 차이로 맞는 후보가 지워질 수 있음). 미리보기에서 눈으로 확인한다. — 내 판단
- 응답 스키마(`SupplementCandidate`)와 프론트는 바꾸지 않는다.

## 제약

- 런타임은 네트워크로 식약처 API를 부르지 않는다. 저장된 파일만 읽는다.
- API 키는 코드·로그·커밋에 넣지 않는다. 요청 URL을 로그에 남길 때 키를 가린다.
- 개인 데이터는 테스트·커밋에 넣지 않는다. 테스트는 합성 원료 몇 개로.
- 테스트 명령: `.venv/bin/python -m pytest tests/runtime tests/risk_model tests/test_users_router.py tests/rag/test_load.py tests/rag/test_kdca.py tests/rag/test_report_preview.py tests/rag/test_grounding.py tests/rag/test_eval_judge.py -q -p no:warnings`
  (새 테스트 파일을 만들면 이 명령에 넣는다).
- 끝나면 `rag/eval/report_preview.py`로 KNHANES 5명 미리보기를 다시 돌려, 위험이 있는 사람에게 영양제 후보가 나오고
  모두 식약처 원료를 인용하는지 확인한다. 미리보기도 앱과 같은 고르기 함수를 써야 한다.

## 방식 (고른 것과 고려한 것)

- **B. 질환·유형 태그로 원료를 바로 고르기 (선택, 사용자 결정)**: 결과가 정해져 있고 검색 기준선 문제가 없다.
  검색 옆에 고르기 경로 하나가 더 생긴다.
- A. 원료를 RAG 조각으로 넣고 질환별 영양제 쿼리로 검색: 지금 흐름을 그대로 쓰지만, 한 줄짜리 조각이 기준선(0.7028)을
  넘을지 불확실하고, 기능성 문구가 거의 같은 원료들(혈당 36개) 사이 순위가 사실상 무작위라 같은 사람에게 다른 후보가 나올
  수 있다.
- 저장 위치: DB 테이블 대신 저장소 JSON 파일(내 판단). 원료 목록은 새 원료 인정 때만 바뀌고 약 180개라, 마이그레이션·
  임베딩 없이 파일로 충분하다. 바뀌면 스크립트를 다시 돌려 커밋·배포한다.

## 빌더에게 맡기는 것

파일 위치·이름과 JSON 모양, 태그 규칙의 정확한 패턴(위 오태깅 테스트 포함), 고르기 함수의 위치와 이름, Evidence의
`chunk_id`·`document_id` 값, 본문 문장 형식, 프롬프트 문구, 테스트 구성.
