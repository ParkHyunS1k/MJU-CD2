# 위험도 변화: 기록별 위험도 저장, 리포트 문장, 위험도 추이 그래프

## 왜

이 서비스는 헬스 계획이 아니라 성인병 조기 관리 서비스다(사용자). 사용자가 리포트를 열었을 때 가장 먼저 봐야 할 숫자는
"내 위험도가 지난번보다 어떻게 바뀌었나"다(사용자 결정). 지금은 질환별 위험도를 측정 시점마다 따로 보여줄 뿐,
변화와 그 이유를 말해주지 않는다. 위험도 화면의 "위험도 변화 추이" 그래프도 자리만 있고 데이터가 없다
(`feature/survey-device-fix` 브랜치 `src/screens/RiskScreen.tsx`, 라벨·값이 하드코딩).

## 목표 / 비목표 / 반목표

- 목표
  1. 측정 기록마다 질환별 위험도를 계산해 DB에 저장한다(사용자 결정).
  2. 리포트에 직전 측정 대비 질환별 위험도 변화(%p)와 그 변화가 BMI·체지방률·나이 중 무엇에서 왔는지 넣는다.
  3. 위험도 추이 그래프가 쓸 API를 만든다: 저장된 기록별 위험도를 읽어 돌려준다.
  4. 위험도 계산의 나이를 측정일 기준으로 바꾼다(사용자 결정).
- 비목표: 위험 모델 재학습·계수 수정, 프론트 화면 수정, 처음 측정 대비 변화.
- 반목표(돌아가도 실패)
  - 저장된 위험도가 기록·프로필 수정 뒤에도 옛 값으로 남는 것.
  - 위험도 계산 실패 때문에 인바디 기록 저장이나 프로필 저장이 실패하는 것. 기록 저장이 우선이다.
  - 변화량 숫자를 GPT가 계산하거나 지어내는 것. 숫자는 코드가 계산하고 GPT는 해석만 한다(기존 원칙).
  - 나이가 늘어 오른 위험을 몸이 나빠진 것처럼 쓰는 것.

## 결정한 것

### 나이: 측정일 기준 (사용자 결정)

`prediction_service._inputs`의 나이를 `date.today().year - birth_year`에서 `측정 연도 - birth_year`로 바꾼다.
- 측정 연도는 기록의 `measured_at`. 없으면 `created_at`, 그것도 없으면 오늘. — 내 판단
- 연 단위 계산(생일 무시)은 지금과 같게 둔다.
- 측정 당시 19세 미만이면 그 기록은 위험도를 계산하지 않는다(아래 "계산 못 하는 기록").
- 영향: 같은 기록이라도 예전 리포트와 위험도 숫자가 달라질 수 있다(오래된 기록일수록 나이가 줄어 대체로 낮아짐).
  리포트 생성(`_analyze_inbody_record`)도 같은 함수로 계산하므로 리포트와 저장값이 일치한다.

### 무엇을 저장하나

`inbody_logs`에 jsonb 컬럼 하나(이름은 빌더가 정함, 예: `disease_risks`)를 추가한다. 질환마다:
`disease`, `disease_key`, `probability`, `risk_level`, 그리고 **모든 입력의 로그 오즈 기여**(`prediction_service._contributions`의
전체 결과: 나이, 성별, BMI, 체지방률, 가족력 3개). 기여는 상위 3개만 남기면 변화 이유를 나눌 수 없어서 전부 저장한다.
`top_factors`는 기여와 프로필로 다시 만들 수 있으니 저장 여부는 빌더가 정한다. 계산에 쓴 나이도 함께 저장한다. — 내 판단

계산 못 하는 기록은 컬럼을 `null`로 둔다.

**계산에 쓴 입력도 함께 저장한다.** 성별, 출생연도, 가족력 3개, 측정 연도, BMI, 체지방률. 읽는 쪽(리포트·그래프)은
저장된 입력이 지금 프로필·지금 행의 값과 다르면 그 기록을 다시 계산해 쓰고 저장한다. 다시 계산이 실패한 기록은
`null`과 같이 "계산 못 함"으로 다룬다. — 내 판단

이유: 아래 "언제 계산해 저장하나"에서 다시 계산이 실패해도 원래 요청은 성공시키므로, 옛 값이 남을 수 있다.
`null`과 달리 옛 값은 겉보기로 구분되지 않아 반목표("옛 값으로 남는 것")를 어기고, 변화 이유 나누기도 깨진다
(한 기록만 옛 프로필이면 가족력·성별 몫이 0이 아니게 됨). 입력을 같이 저장하면 읽을 때 낡은 값을 가려낼 수 있어,
트리거가 실패해도 다음에 읽을 때 바로잡힌다.

### 언제 계산해 저장하나

| 상황 | 할 일 |
|---|---|
| 기록 생성 (`create_inbody_record`, `create_inbody_from_upload`) | 저장 직후 계산해 같은 행에 기록 |
| 기록 수정 (`update_inbody_record`) | 수정할 때마다 다시 계산. 어떤 필드가 바뀌었는지 따지지 않는다. — 내 판단 |
| 프로필 수정 (`PATCH /users/me`) | `gender`, `birth_year`, `fh_*` 중 하나라도 요청에 있으면 그 사용자의 모든 기록을 다시 계산(사용자 제안) |
| 기존 기록 | 마이그레이션 뒤 한 번 채우는 스크립트 |

- 계산·저장이 실패하면 로그만 남기고 원래 요청(기록 저장, 프로필 저장)은 성공으로 돌려준다(반목표).
  그 기록은 `null`이거나 옛 값일 수 있으므로, 읽는 쪽은 위의 입력 비교로 옛 값을 가려내 다시 계산한다.
- 프로필 수정 트리거는 앱 코드(라우터나 서비스)에서 한다. DB 트리거는 쓰지 않는다(모델이 Python에 있음).

### 계산 못 하는 기록

`predict_all`이 빈 목록을 주거나(BMI·체지방률 없음) `ValueError`를 내는 경우(성별·출생연도 없음, 측정 당시 19세 미만,
BMI 12–60·체지방률 3–70 범위 밖 = OCR 오독으로 보는 값) → `null`로 저장. 프로필이 채워지면 프로필 트리거가 다시 계산한다.

### 리포트: 직전 대비 변화

- 대상 기록: 저장된 위험도를 읽는다. `null`이면 지금처럼 계산해 리포트에 쓰고 그 행에도 저장한다. — 내 판단
  (계산이 실패하면 지금과 같은 400/422)
- 직전 기록: 대상보다 `measured_at`이 이른 기록 중 가장 최근 것으로, 저장된 위험도가 `null`이 아닌 것. 리포트 유무는 보지 않는다.
  없으면(첫 측정 등) 변화 항목을 넣지 않는다.
- 변화 이유: 모델이 로지스틱 회귀라 입력별 로그 오즈 기여를 더하면 정확히 전체 로그 오즈다. 두 기록의 기여 차이 Δc가
  로그 오즈 변화를 남김없이 나눈다. 가족력·성별은 지금 프로필로 다시 계산되므로 두 기록이 같고(Δc = 0),
  차이는 BMI, 체지방률, 나이에서 나온다.
  - 확률 변화 Δp(%p)를 로그 오즈 몫에 비례해 나눈다: 요인 f의 몫 = Δp × Δc_f / ΣΔc. 몫의 합은 정확히 Δp.
  - ΣΔc = 0이면 몫을 내지 않는다. 두 요인이 반대 방향이면 몫 하나가 Δp보다 커질 수 있다. 그대로 둔다. — 내 판단
- `generate_report`의 사용자 데이터(payload)에 `risk_change`를 추가한다. 질환마다: 질환명, 직전 측정일, 직전·지금 확률,
  변화 %p, BMI 몫·체지방률 몫·나이 몫 %p, 직전·지금 BMI와 체지방률. 소수 첫째 자리로 반올림.
- 프롬프트 규칙: `risk_report`의 각 message에 `risk_change`가 있으면 변화와 주된 이유를 한 번 쓴다
  (예: "지난 측정(2025-06-02)보다 4.1%p 낮아졌고, 대부분 체지방률 감소(3.0%p) 덕분이에요"). 사용자 데이터라 인용하지 않는다.
  - |변화| < 1.0%p면 "지난번과 비슷"으로 쓴다. — 1.0%p는 내 판단
  - 나이 몫은 "나이가 들며 자연히 늘어난 몫"으로 구분해 쓰고, 몸의 변화와 섞지 않는다(반목표).
- 응답 스키마(`AIReportContent`, `HealthReport`)에는 필드를 추가하지 않는다. — 내 판단

### 위험도 추이 API

- `GET /inbody/risk-trend` (로그인 사용자). 경로 이름은 빌더가 바꿔도 된다. `/inbody/{inbody_id}`보다 먼저 등록한다.
- 저장된 값을 읽는다. 저장된 입력이 지금 값과 다른 기록만 다시 계산해 저장한다(위 규칙). 측정일 오름차순 목록, 항목마다 `inbody_id`, `measured_at`, 질환별
  `disease`, `disease_key`, `probability`, `risk_level`. 기여는 넣지 않는다. — 내 판단
- 위험도가 `null`인 기록은 뺀다. 기록이 없으면 빈 목록(200).

## 제약

- 위험 모델과 학습 산출물(`models/`)은 건드리지 않는다. 나이 입력을 만드는 방식만 바뀐다.
- DB 마이그레이션은 `supabase/migrations/`에 파일로 두고, 원격 적용과 기존 기록 채우기는 사용자 확인 뒤에 한다.
  순서는 마이그레이션 적용 → 코드 푸시(배포)다. 새 컬럼이 없는 DB에서 새 코드가 도는 경우는 대비하지 않는다. — 내 판단
- 개인 데이터(실제 사용자 기록)를 테스트·커밋에 넣지 않는다. 테스트는 합성 값으로.
- 테스트 명령: `.venv/bin/python -m pytest tests/runtime tests/risk_model tests/test_users_router.py tests/rag/test_load.py tests/rag/test_kdca.py tests/rag/test_report_preview.py tests/rag/test_grounding.py tests/rag/test_eval_judge.py -q -p no:warnings`
  나이 기준이 바뀌어 기존 테스트의 기대값이 달라지면, 새 기준에 맞게 고치고 그 이유를 커밋 메시지에 쓴다.
