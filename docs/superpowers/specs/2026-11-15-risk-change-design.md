# 위험도 변화: 리포트 문장과 위험도 추이 그래프

## 왜

이 서비스는 헬스 계획이 아니라 성인병 조기 관리 서비스다(사용자). 사용자가 리포트를 열었을 때 가장 먼저 봐야 할 숫자는
"내 위험도가 지난번보다 어떻게 바뀌었나"다(사용자 결정). 지금은 질환별 위험도를 측정 시점마다 따로 보여줄 뿐,
변화와 그 이유를 말해주지 않는다. 위험도 화면의 "위험도 변화 추이" 그래프도 자리만 있고 데이터가 없다
(`feature/survey-device-fix` 브랜치 `src/screens/RiskScreen.tsx`, 라벨·값이 하드코딩).

## 목표 / 비목표 / 반목표

- 목표
  1. 리포트에 직전 측정 대비 질환별 위험도 변화(%p)와 그 변화가 BMI·체지방률 중 무엇에서 왔는지 넣는다.
  2. 위험도 추이 그래프가 쓸 API를 만든다: 사용자의 모든 측정 기록별 질환 위험도.
- 비목표: 위험 모델 수정, 나이 계산 방식 수정(아래 제약), 프론트 화면 수정, 처음 측정 대비 변화.
- 반목표(돌아가도 실패)
  - 나이·가족력 같은 몸 이외의 차이가 "몸이 바뀌어서 위험이 바뀌었다"로 보이는 것.
  - 변화량 숫자를 GPT가 계산하거나 지어내는 것. 숫자는 코드가 계산하고 GPT는 해석만 한다(기존 원칙).
  - 위험도를 DB에 따로 저장해 기록·프로필 수정 뒤 낡은 값이 남는 것.

## 결정한 것

### 다시 계산한다, 저장하지 않는다 (사용자 결정)

위험도는 측정값과 프로필만으로 정해지는 순수 계산이고(로지스틱 회귀, 질환 4개 합쳐 호출당 약 0.9 ms),
모델은 앞으로 바뀌지 않는다(사용자). 그래서 필요할 때마다 `predict_all`로 다시 계산한다.
- 지난 리포트에 저장된 `disease_risks`는 쓰지 않는다. 리포트 없는 기록이 있고(9건 중 2건), 저장 당시 나이가
  리포트 생성일 기준이며, 요인이 상위 3개만 저장돼 변화 이유를 나눌 수 없다.
- 위험도 저장 컬럼은 만들지 않는다.

### 두 용도, 두 범위 (사용자 결정)

| 용도 | 계산하는 기록 | 언제 |
|---|---|---|
| 리포트 문장 | 대상 기록과 그 직전 기록 1건 | 리포트 생성 때 (`_analyze_inbody_record`) |
| 위험도 추이 그래프 | 사용자의 모든 기록 | 그래프 요청 때 (새 GET 엔드포인트) |

그래프 데이터를 리포트에 넣지 않는다. 넣으면 리포트를 다시 만들기 전까지 그래프가 갱신되지 않는다.

### 직전 기록

대상 기록보다 `measured_at`이 이른 기록 중 가장 최근 것으로, 위험도를 계산할 수 있는 것. 리포트 유무는 보지 않는다.
없으면(첫 측정 등) 변화 항목 자체를 넣지 않는다.

"계산할 수 있다"는 BMI·체지방률이 모두 있고 `_check_range` 범위(BMI 12–60, 체지방률 3–70) 안이라는 뜻이다.
범위 밖은 OCR 오독으로 보는 값이라, 그 기록은 건너뛰고 더 이전 기록을 본다. 옛 기록 하나가 잘못 읽혔다고
지금 기록의 리포트가 실패하면 안 된다. — 내 판단

### 같은 프로필로 계산

두 기록 모두 지금 사용자 프로필(성별·출생연도·가족력)로 계산한다. 나이는 `predict_all`이 오늘 연도로 계산하므로
두 기록에 같은 나이가 들어간다. 그래서 차이는 BMI·체지방률에서만 나온다. 프로필을 고쳐도 낡은 값이 없다.

### 변화 이유 나누기

모델이 로지스틱 회귀라 요인별 로그 오즈 기여(`prediction_service._contributions`, SHAP과 같음)를 더하면 정확히
전체 로그 오즈가 된다. 두 기록의 기여 차이 Δc_bmi, Δc_pbf가 로그 오즈 변화를 남김없이 나눈다(다른 입력은 같으므로 0).
확률 변화 Δp(%p)를 로그 오즈 몫에 비례해 나눈다: 요인 f의 몫 = Δp × Δc_f / (Δc_bmi + Δc_pbf).
- 두 몫의 합은 정확히 Δp다.
- Δc_bmi + Δc_pbf = 0이면(로그 오즈가 그대로) 몫을 내지 않는다.
- 두 요인이 반대 방향이면 몫 하나가 Δp보다 커질 수 있다. 그대로 둔다(합은 맞음). — 내 판단

`_contributions`는 지금 `predict_all` 안에서만 쓰이고 결과는 상위 3개만 나온다. 두 요인의 기여를 꺼낼 공개 함수가
`prediction_service`에 필요하다. 형태는 빌더에게 맡긴다.

### 리포트에 넣는 방식

- `generate_report`의 사용자 데이터(payload)에 `risk_change`를 추가한다. 질환마다: 질환명, 직전 측정일, 직전 확률,
  지금 확률, 변화 %p, BMI 몫 %p, 체지방률 몫 %p, 직전·지금 BMI와 체지방률. 소수 첫째 자리로 반올림한다.
- 프롬프트 규칙: `risk_report`의 각 message에 `risk_change`가 있으면 변화와 주된 이유를 한 번 쓴다
  (예: "지난 측정(2025-06-02)보다 4.1%p 낮아졌고, 대부분 체지방률 감소(3.0%p) 덕분이에요"). 사용자 데이터라 인용하지 않는다.
  |변화| < 1.0%p면 "지난번과 비슷"으로 쓴다. — 1.0%p는 내 판단
- 응답 스키마(`AIReportContent`, `HealthReport`)에는 필드를 추가하지 않는다. 숫자를 화면에 따로 보여줄 자리가 프론트에 없고,
  그래프는 아래 API가 맡는다. — 내 판단

### 위험도 추이 API

- `GET /inbody/risk-trend` (로그인 사용자). 경로 이름은 빌더가 바꿔도 된다. `/inbody/{inbody_id}`보다 먼저 등록한다.
- 응답: 측정일 오름차순 목록. 항목마다 `inbody_id`, `measured_at`, 질환별 `disease`, `disease_key`, `probability`, `risk_level`.
  `top_factors`는 넣지 않는다(그래프에 필요 없음). — 내 판단
- BMI·체지방률이 없거나 범위 밖인 기록은 뺀다(위 "직전 기록"과 같은 기준). 기록 하나 때문에 그래프 전체가 400이 되면 안 된다.
- 성별·출생연도가 없거나 19세 미만이면(프로필 문제라 모든 기록에 해당) 400과 그 메시지.
  `predict_all`은 두 경우 모두 `ValueError`를 내므로, 프로필 검사를 기록별 계산과 구분해야 한다.
- 기록이 없으면 빈 목록(200).

## 제약

- `prediction_service._inputs`의 나이는 측정일이 아니라 오늘 연도 기준이다. 이번에는 바꾸지 않는다(사용자와 합의).
  이 덕분에 두 기록의 나이가 같아진다는 점을 코드 주석에 남긴다.
- 위험 모델과 학습 산출물(`models/`)은 건드리지 않는다.
- 개인 데이터(실제 사용자 기록)를 테스트·커밋에 넣지 않는다. 테스트는 합성 값으로.
- 테스트 명령: `.venv/bin/python -m pytest tests/runtime tests/risk_model tests/test_users_router.py tests/rag/test_load.py tests/rag/test_kdca.py tests/rag/test_report_preview.py tests/rag/test_grounding.py tests/rag/test_eval_judge.py -q -p no:warnings`

## 프론트에 넘길 것 (이번 범위 밖)

`RiskScreen.tsx`의 "위험도 변화 추이"에 새 API를 연결하고, 고정 라벨("3개월 전…") 대신 측정 날짜를 쓴다
(측정 간격이 일정하지 않음). 프론트 담당자에게 API 형태를 전달한다. — 내 판단(사용자가 답하지 않은 부분)

엔드포인트를 둘 서비스 모듈, 프롬프트 문구, 테스트 구성.
