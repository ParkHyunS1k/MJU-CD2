# 리포트 개인화: 개인 지표와 특성 쿼리

- 날짜: 2026-10-28
- 상태: 승인 (2026-10-28)
- 관련: `2026-10-15-rag-runtime-design.md`(검색·인용), `2026-10-12-risk-model-redesign-design.md`(위험도 모델, 타겟 정의)

## 1. 배경과 이유

KNHANES 2023에서 고른 5명으로 리포트를 만들어 보니(2026-10-28), 고혈압·지질·당뇨 위험이 높은 세 사람의 "맞춤형 개선 가이드"가 거의 같았다. 세 리포트 모두 같은 근거 문단 4개(포털 고혈압 식이요법, 이상지질혈증 지침 p.85, 고혈압 지침 p.77, 당뇨병 지침 p.18)를 썼다. 사용자 말로는 "모든 사람에게 똑같이 답하면 AI를 쓰는 이유가 없다. 지침서를 보면 된다."

원인은 GPT가 아니라 입력이다.

1. **검색이 같다.** 쿼리가 "고혈압 예방 식이요법 식사 관리"처럼 질환·분야별 고정 문구라, 같은 질환 위험인 사람은 같은 청크를 받는다.
2. **개인 숫자를 GPT가 직접 계산한다.** 프롬프트 수정(커밋 6009a9e) 뒤 "74.9 kg의 5% = 3.7 kg" 같은 문장이 나왔지만, 계산은 검증되지 않고 체중 감량 하나에서 멈췄다.
3. **없는 값을 해석한다.** 골격근량이 없는 사람에게 "골격근량 측정값 없음 [낮음]" 주의점을 만들었다.

조사한 해법(출처는 대화 기록): 검색 전에 사용자 특성으로 쿼리를 개인화(Personalize Before Retrieve, AAAI 2025), 숫자는 코드로 먼저 계산해 LLM에 넘김(Google PHIA·Personal Health Agent). 생활습관 설문(JMIR 2025)은 이번 범위 밖이다.

## 2. 목표

- 같은 위험 유형이어도 사람마다 받는 근거와 리포트의 개인 수치가 달라진다.
- 개인 수치(목표 체중, 기준까지 남은 양 등)는 코드가 계산하고 테스트로 검증한다. GPT는 계산하지 않는다.
- 기존 검색 품질(평가로 고른 쿼리·임계값·k)을 깨지 않는다.

**비목표**
- 생활습관 설문(흡연·음주·운동 습관). 다음 단계.
- 사진 인식(OCR) 변경. 다른 팀원이 맡는다. 이번에는 DB 컬럼만 추가한다.
- LLM으로 쿼리 다시 쓰기, 청크에 대상(나이·성별) 메타데이터 붙이기.
- 프론트 변경. 출처 표시·"전반적 위험도" 버그는 프론트 담당에게 따로 전달한다.

**반대 목표(이렇게 되면 실패)**
- 개인화한다며 없는 수치를 지어내는 것.
- 코드에 넣은 기준값이 근거 인용 없이 권고처럼 리포트에 나가는 것.
- 특성 쿼리 때문에 기존 질환 근거가 빠지는 것.

## 3. 타겟 사용자

위험도 모델 설계 1절의 타겟: **30대 전후의 성인병 초기 위험군. 50대 이상은 타겟이 아니다.** 특성은 이 사람들에게 흔한 "아직 병은 아니지만 조짐이 있는" 상태로 고른다. 노인·폐경 같은 특성은 넣지 않는다.

## 4. 사용자가 정한 것

| 항목 | 결정 |
|---|---|
| 쿼리 방식 | 기존 질환 쿼리는 그대로 두고 특성 쿼리를 **더한다** |
| 특성 | 타겟(30대 전후 초기 위험군)에 맞춘다 |
| 근육 특성 | 결과지의 "근육조절" 값으로 판단한다(선택지 b) |
| DB | `inbody_logs`에 `height`, `muscle_control` 컬럼 추가. OCR은 다른 사람이 채운다 |
| 리포트 생성 | GPT API(`gpt-6.1-terra`) |

## 5. 설계

### 5.1 DB: `inbody_logs` 컬럼 2개, 검색 RPC가 청크 분야 반환

마이그레이션 하나에 다음을 담는다.

- `height numeric` — 신장(cm). 결과지 상단 "신장".
- `muscle_control numeric` — 결과지 "체중조절" 칸의 "근육조절"(kg). 양수면 인바디 기준으로 근육을 그만큼 늘려야 표준, 0이면 표준.
- 둘 다 nullable. 기존 행은 null.
- (2026-10-28 사용자 요청으로 확장) 결과지의 나머지 수치도 저장한다: 인바디점수, 적정체중, 체중조절, 지방조절, 제지방량, 비만도, 권장섭취열량, 비만평가(BMI·체지방률, 글자), 부위별 근육·체지방(JSON), 임피던스(JSON). 표준 범위와 운동소비열량은 키·성별·체중으로 계산되는 참고값이라, 회원번호는 개인정보라 저장하지 않는다. 리포트 입력에는 아직 쓰지 않는다.
- `match_rag_chunks`가 `category`(청크 자신의 분야)도 돌려주게 한다. 반환 형식이 바뀌므로 함수를 지우고 다시 만든다(권한도 다시 준다: service_role만).

백엔드 스키마(`InBodyMetricsBase`)에 두 필드를 추가해 생성·수정·조회 API로 오가게 한다. `InBodyExtraction`(OCR 출력)은 건드리지 않는다. OCR 담당에게 "두 필드를 읽어 넣으면 된다"고 알린다.

**영양제 인용 구멍 수정:** 지금 `Evidence.category`는 그 청크를 찾은 *쿼리*의 분야다. 영양제 쿼리가 식사 문단을 찾아오면 그 문단이 "영양제 근거"로 취급돼 영양제 인용 검사(`citation_service`)를 통과한다. 지금까지는 영양제 쿼리가 없어서 드러나지 않았다. `Evidence`에 청크 자신의 분야(`chunk_category`)를 추가하고, 영양제 인용 검사는 이것을 본다. 쿼리 분야는 근거 머리글 표시용으로 남긴다.

### 5.2 개인 지표 (`app/services/personal_metrics.py`, 신규)

`compute(inbody: dict, profile: dict) -> dict`. 결과는 리포트 payload의 `personal_metrics`로 들어가고, 특성 판단(5.3)도 이 결과를 쓴다.

| 키 | 계산 | 없을 때 |
|---|---|---|
| `height_cm` | `height`가 있으면 그 값, 없으면 √(체중 ÷ BMI) × 100, 소수 첫째 자리. `height_source`: `"measured"`/`"derived"` | 체중이나 BMI가 없으면 생략 |
| `bmi_band` | 대한비만학회 기준: <18.5 저체중, 18.5–22.9 정상, 23–24.9 비만 전단계, 25–29.9 1단계 비만, 30–34.9 2단계, ≥35 3단계 | BMI 없으면 생략 |
| `kg_to_normal_bmi` | BMI 23 이상이면, BMI 22.9가 되는 체중까지 줄여야 할 kg | 그 외 생략 |
| `weight_loss_5pct_kg`, `weight_loss_10pct_kg` | BMI 23 이상이면 체중의 5%·10%(kg, 소수 첫째 자리)와 그때의 체중 | 그 외 생략 |
| `body_fat_status` | 인바디 결과지 "비만평가" 기준. 남: <10 낮음, 10–20 표준, 20–25 경도비만, >25 비만. 여: <18, 18–28, 28–33, >33. 표준 상한을 넘은 %p도 함께 | 체지방률 없으면 생략 |
| `muscle_status` | `muscle_control` > 0이면 "표준 이하"와 늘릴 kg, 0이면 "표준" | null이면 생략 |
| `abdominal` | 복부지방률 ≥ 0.90(남)/0.85(여), 내장지방레벨 ≥ 10이면 해당 항목과 값 | 둘 다 없으면 생략 |
| `missing_metrics` | 리포트 입력 인바디 11개 중 값이 없는 항목의 한국어 이름 목록 | 항상 있음(빈 목록 가능) |

기준값은 상수로 모으고 출처를 주석에 적는다. BMI 단계는 코퍼스에 있는 대한비만학회 기준(포털 문서와 학회 문서)이다. 체지방률은 코퍼스에 기준이 없어 인바디 결과지 기준을 쓴다. 이 값은 의학 지침이 아니라 기기 기준이므로, 리포트에서 "인바디 기준"으로만 표현하게 한다(5.4).

복부·BMI 기준은 `rag_taxonomy`의 `OBESITY_BMI`, `ABDOMINAL_RATIO`, `VISCERAL_FAT_LEVEL`과 같은 값이므로 한 곳에 두고 함께 쓴다.

### 5.3 특성 쿼리 (`rag_taxonomy`)

`build_queries`가 기존 질환 쿼리에 특성 쿼리를 더한다. 특성 쿼리는 **목록 뒤**에 둔다. 근거 상한이 쿼리 수 이상이라 모든 쿼리의 1위는 순서와 관계없이 들어가고, 순서는 2위 이하에만 영향을 준다. 앞에 두면 특성의 2위가 질환의 2·3위를 밀어내 반대 목표에 걸린다(최종 코드 검토에서 발견, 처음엔 앞에 두기로 했다).

| 특성 | 판단 | 쿼리 문구 | 태그(질환·분야) |
|---|---|---|---|
| 근육 부족 | `muscle_status` 표준 이하 | 근육량 증가 저항운동 단백질 섭취 | sarcopenia · exercise |
| 체지방 과다(BMI 23 미만) | BMI < 23이고 `body_fat_status`가 경도비만 이상 | 체지방률 감소 근력운동 체성분 개선 | obesity · exercise |
| 복부비만 | `abdominal`에 해당 항목 있음 | 복부비만 내장지방 감소 운동 식사 | metabolic_syndrome · lifestyle |
| 전단계 위험 | 위험도 medium인 질환마다 | 고혈압 전단계 주의혈압 생활습관 교정 / 당뇨병 전단계 공복혈당장애 예방 / 이상지질혈증 경계 수치 생활습관 교정 | 해당 질환 · lifestyle |
| 가족력 | 프로필 가족력 true인 질환마다 | {질환} 가족력 고위험군 조기 예방 | 해당 질환 · lifestyle |
| 여러 위험 동반 | medium 이상 질환 2개 이상 | 대사 위험인자 동반 생활습관 관리 | metabolic_syndrome · lifestyle |
| 체중 증가 추세 | 추세 분석에서 체중 또는 체지방률이 악화 | 체중 증가 예방 체중 유지 관리 | obesity · lifestyle |
| 비만 전단계 | BMI 23–24.9 | 비만 전단계 과체중 체중 증가 예방 | obesity · lifestyle |
| 영양제 | 항상 | 영양제 건강기능식품 선택 주의사항 | general · supplement |

- 특성 쿼리는 **최대 4개 + 영양제 1개**만 쓴다. 고콜레스테롤과 고중성지방은 둘 다 이상지질혈증 하나로 친다.
- 개수는 **쿼리 수**로 세되, 위 표 순서대로 **특성 종류마다 1개씩 먼저** 고르고 자리가 남으면 같은 종류의 두 번째 쿼리(예: 두 번째 질환의 가족력)를 넣는다. 질환이 여러 개인 특성(전단계, 가족력)이 자리를 다 차지해 다른 특성이 사라지는 것을 막기 위해서다. (구현자 검토에서 나온 질문, 내 판단)
- `Query`에 특성 이름(`trait`, 예: "가족력")을 추가한다. 근거 머리글은 특성 쿼리면 `(가족력·생활습관)`처럼 특성 이름을 보여 준다.
- 근거 상한은 **쿼리마다 1위 근거가 반드시 들어가도록** `max(15, 쿼리 수)`로 둔다. 질환 쿼리 최대 16개 + 특성 5개 = 21개이므로 최대 21개다. 고정값 18이면 질환 쿼리가 많은 사람은 뒤쪽 질환 쿼리 3개가 1위 근거도 받지 못해 반대 목표("특성 쿼리 때문에 기존 질환 근거가 빠지는 것")에 걸린다. 입력 토큰은 최악의 경우 약 40% 늘어난다. 근거 중복이 많아 실제로는 그보다 적다. (구현자 검토에서 나온 질문, 내 판단)
- 문구는 평가에 쓴 키워드형 쿼리와 같은 형식(명사 나열)으로 쓴다. 임계값 0.7028을 넘지 못한 특성 쿼리는 근거를 못 가져올 뿐 오류는 아니다.

### 5.4 프롬프트

- payload에 `personal_metrics`를 넣는다.
- 지시문에서 "근거의 일반 권고는 사용자 수치에 적용해 개인 목표로 바꾸세요(예: 감량 비율은 이 사람의 체중으로 kg을 계산…)"를 "개인 목표 수치는 `personal_metrics`의 값을 그대로 쓰고 직접 계산하지 마세요"로 바꾼다. 권고 자체(예: "5~10% 감량")는 지금처럼 근거에서 인용한다.
- "`missing_metrics`에 있는 지표는 해석하거나 항목으로 만들지 마세요"를 추가한다.
- **감량 목표 수치(사용자 결정):** "`weight_loss_5pct_kg`·`weight_loss_10pct_kg`는 체중 감량 권고를 [근거]에서 인용한 항목에서만 쓰고, 그런 근거가 없으면 `kg_to_normal_bmi`를 '정상 BMI까지 x kg'이라는 설명으로만 쓰세요"를 추가한다. BMI 23 이상이면 감량 근거를 찾는 쿼리(비만 질환 쿼리 또는 비만 전단계 특성)가 항상 들어가므로 대부분 근거가 있다.
- "`body_fat_status`와 `muscle_status`는 인바디 기준이라고 밝히세요"를 추가한다.
- 나머지 규칙(위험 높은 질환마다 항목 1개, SHAP 순서, 같은 S번호 반복 금지)은 유지한다.

### 5.5 검증

검증 데이터와 스크립트:
- 5명은 KNHANES 2023에서 위험 유형별 규칙으로 고른다(고혈압 높음·실제 고혈압 / 당뇨 높음·실제 당뇨 / 3개 이상 높음·BMI 30 이상 / 고중성지방 주의·BMI 23 미만 / 모두 낮음·여성). 지금은 대화 중에 만든 임시 스크립트로 골랐으므로, 이 선정·생성·비교 스크립트를 `rag/eval/` 아래로 옮겨 커밋한다(개인 원자료와 결과물은 커밋하지 않는다).
- 바꾸기 전 리포트는 커밋 6009a9e로 이미 만든 결과(임시 폴더의 `preview_a.json`)를 기준으로 쓴다. GPT 출력은 매번 달라지므로, 비교 수치는 "참고"로만 보고하고 3b 비교 평가에서 여러 사례로 다시 잰다.
- 사용자 결과지 2장의 `height`, `muscle_control`은 결과지에 적힌 값을 손으로 넣는다(둘 다 근육조절 0.0이라 근육 특성은 켜지지 않는다). 근육 특성은 단위 테스트의 가상 입력으로 확인한다.

1. **단위 테스트:** 개인 지표 계산(키 역산, BMI 단계 경계값, 감량 kg, 체지방·근육 상태, 누락 목록), 특성 판단과 우선순위·개수 제한, 특성 쿼리가 질환 쿼리보다 앞에 오는지, 영양제 인용이 청크 분야로 걸러지는지, 마이그레이션 뒤 스키마 왕복.
2. **검색 확인:** KNHANES 5명 + 사용자 기록 2개(첫 장·마지막 장)로 특성 쿼리마다 임계값 통과 여부와 가져온 청크를 표로 본다. 특성과 맞지 않는 청크가 많으면 문구를 고친다.
3. **개인화 비교:** 같은 5명 리포트를 바꾸기 전(커밋 6009a9e)과 후로 비교한다.
   - 사람들 사이 인용 청크 겹침(쌍별 Jaccard 평균)
   - "사용자 수치가 들어간 행동 권고" 비율
   - 없는 지표를 해석한 항목 수(목표 0)
   - 리포트는 프론트 리포트 화면 섹션 순서로 사용자에게 보여 준다.

## 6. 위험과 한계

- **임베딩 한도:** 리포트 1건의 쿼리가 최대 약 21개로 늘어난다. Gemini 임베딩 무료 등급(하루 1,000건)으로는 하루 약 45건이 한도다. 시연에는 충분하고, 배포 전에 유료 등급을 권한다.
- **근육 특성은 OCR이 `muscle_control`을 채워야 동작한다.** 그 전까지는 값이 null이라 이 특성이 켜지지 않는다.
- **체지방률 기준은 인바디 기기 기준이다.** 의학 지침이 아니라는 점을 리포트에서 밝힌다.
- **특성 쿼리에는 정답 라벨이 없다.** 이번에는 5.5의 눈검사로 확인하고, 3b 비교 평가 때 라벨 보강 대상에 넣는다.
