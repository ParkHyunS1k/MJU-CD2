# RAG 검색 평가 하네스와 모델 선정 설계 (하위 프로젝트 2)

- 작성일: 2026-10-11 (후보 모델은 2026-10-11 웹 조사로 갱신)
- 상태: 검토 대기
- 상위 설계: `docs/superpowers/specs/2026-10-08-rag-report-design.md` 10.1절, 11절
- 입력: 하위 프로젝트 1의 `rag/data/chunks.jsonl` (문서 16개, 청크 588개, 2026-10-11 기준)

**용어**: 이 문서의 "쿼리"는 **검색 쿼리(검색어)**다. 벡터DB에서 청크를 찾을 때 임베딩해 쓰는 짧은 문장이며, LLM에 보내는 프롬프트가 아니다. 이 평가는 "검색 쿼리 → 청크 검색" 단계만 측정한다.

## 1. 목표

리포트 생성 시 쓸 검색 구성(파서, 청킹, 임베딩, 하이브리드, 리랭커, k, 임계값)을 **우리 코퍼스와 우리 쿼리로 측정해서** 고른다. 결과는 캡스톤 보고서에 쓸 비교표와, 하위 프로젝트 3이 읽을 최종 설정 파일이다.

**비목표**
- 유료 API 모델 비교(필요해지면 3단계에 후보만 추가)
- 생성 품질 평가(RAG 없음 vs 전체 넣기 vs RAG, 상위 설계 10.2절). 리포트 생성 연결 이후로 미룬다.
- 운영 DB(pgvector) 적재. 실험은 로컬 numpy 전수 검색으로 한다.

## 2. 결정 사항

| 항목 | 결정 |
|---|---|
| 형태 | 파이썬 스크립트 + JSONL 파일, numpy 전수 검색, 결과는 마크다운 표 |
| 후보 범위 | 무료만: Gemini 임베딩(키 보유), 로컬 실행 모델 |
| 정답 라벨 | **근거 문장(span)**: 쿼리마다 답이 되는 원문 문장 1~3개 (상위 설계의 "문서 + 쪽 범위"를 대체) |
| 라벨 만드는 법 | 후보 모으기(pooling) → Gemini 1차 판정 + 근거 문장 추출 → 사용자 직접 검수 |
| 검수 화면 | claude.ai 비공개 아티팩트(공유 DB 저장) |
| 쿼리 | 50개 내외. 조정용 25 / 시험용 25로 분할 |
| 판단 기준 | 부트스트랩 95% 신뢰구간이 겹치면 더 단순·저렴한 쪽을 선택 |

## 3. 정답 라벨: 근거 문장 방식

```json
{"query_id": "q12", "doc_id": "kha-hypertension-2026", "page": 74,
 "evidence": "하루 소금 섭취량을 5 g(나트륨 2,000 mg) 이하로 제한한다.", "source": "human"}
```

- **채점 규칙**: 검색된 청크가 같은 `doc_id`이고, 근거 문장의 **50% 이상**을 포함하면 그 근거를 찾은 것으로 본다. 비교는 공백을 모두 제거하고 NFC 정규화한 문자열로 한다(띄어쓰기가 사라지는 PDF와 파서 차이에 영향받지 않도록).
- **포함 비율 계산**: 근거 문장(공백 제거)의 문자 10-gram 중 청크(공백 제거)에 나타나는 비율. 근거가 10자 미만이면 전체 문자열 포함 여부로 판단한다.
- 한 쿼리에 근거가 여러 개면, 쿼리 단위 지표는 "근거 중 하나 이상을 찾았는가"(Recall, MRR)와 "찾은 근거의 비율"(근거 Recall)을 함께 낸다.
- **청킹과 무관**: 청킹 방식을 바꿔도 라벨을 그대로 쓴다. 청크 번호나 쪽 범위보다 정밀하다(쪽 범위는 당뇨 지침에서 쪽당 청크 약 3개라 너무 거칠다).

## 4. 쿼리 세트 (`rag/eval/queries.jsonl`)

1. **시나리오**: 코퍼스에 자료가 있는 질환 × 카테고리 조합 약 22개

   | 질환 | 카테고리 |
   |---|---|
   | hypertension | criteria, diet, lifestyle, exercise |
   | diabetes | diet, exercise, lifestyle |
   | dyslipidemia | criteria, diet, lifestyle, exercise |
   | obesity | criteria, lifestyle, exercise |
   | metabolic_syndrome | criteria, lifestyle |
   | fatty_liver | criteria, diet, exercise, lifestyle |
   | sarcopenia | criteria, exercise |
   | general | diet, exercise |

2. **조합마다 두 형태**(약 44개)
   - 키워드형: 상위 설계 7.3절의 쿼리 생성 규칙을 흉내 낸 템플릿(예: `고혈압 예방 체지방 감량 식이요법`). 코드로 생성해 결정적이다.
   - 질문형: 사람 말투(예: `고혈압 위험이 있으면 소금을 하루에 얼마나 줄여야 하나요?`). Gemini가 초안을 쓰고 검수 화면에서 사용자가 확인·수정한다.
3. **인바디 특화 쿼리 약 3개**: 여러 문서에 걸치는 실제 상황(예: `체지방률 32% 40대 여성 비만 기준`).
4. **정답 없는 쿼리 약 3개**: 코퍼스에 없는 주제(예: `통풍 식이요법`). 유사도 임계값 보정용.
5. **분할**: 쿼리를 조정용(25)과 시험용(25)으로 고정 분할한다(같은 시나리오의 두 형태는 같은 쪽에 둔다). 모델·구성 선택은 50개 전체로, k와 임계값은 조정용으로 정하고 시험용으로 최종 보고한다.

필드: `query_id, text, form(keyword|question|inbody|unanswerable), condition, category, split(tune|test)`

## 5. 라벨 만들기

### 5.1 후보 모으기 (pooling)
쿼리마다 기준 청킹(PyMuPDF, 1,200자/150자)에서 후보 검색 방식들(임베딩 후보 전부 + BM25)의 **상위 5개씩**을 모아 중복을 제거한다. 쿼리당 10~15개, 전체 약 600개.

한계: 어떤 방식도 찾지 못한 정답은 라벨에서 빠진다(TREC식 pooling의 일반적 한계). 보고서에 명시한다.

### 5.2 Gemini 1차 판정
- 입력: 쿼리, 청크 본문. 출력(JSON 스키마): `{"relevant": bool, "evidence": [청크에서 그대로 복사한 문장]}`
- 근거 문장이 청크에 실제로 들어 있는지(3절 규칙, 100% 포함) 코드로 확인하고, 들어 있지 않은 문장은 버린다.
- 모델: gemini-2.5-flash(기존 키). 결과는 캐시 파일에 저장해 재실행 시 다시 호출하지 않는다.

### 5.3 사람 검수 (비공개 아티팩트)
- 화면: 쿼리 → 후보 청크 목록. 청크를 문장 단위로 보여주고 Gemini가 고른 근거를 강조한다.
- 조작: [맞음] / [관련 없음], 문장 클릭으로 근거 추가·해제, 질문형 쿼리 문구 수정, 쿼리 제외.
- 진행 상태는 아티팩트 공유 DB에 저장되어 나눠서 검수할 수 있다.
- 검수가 끝나면 DB를 읽어 `rag/eval/labels.jsonl`로 내보내고 커밋한다. 검수하지 않은 항목은 라벨에 넣지 않는다.
- 예상 소요: 약 600건 × 10초 ≈ 1.5~2시간.

### 5.4 라벨 보강 (청킹·모델을 나중에 바꿀 때)
새 구성의 상위 결과 중 기존 후보에 없던 텍스트(기존 근거와 겹치지 않는 청크)만 모아 5.2·5.3을 다시 돈다. 전체를 다시 검수하지 않는다.

## 6. 실험

한 번에 한 변수만 바꾸고 각 단계 1등을 다음 단계의 기준으로 쓴다.

| 단계 | 비교 | 고정 | 주요 지표 |
|---|---|---|---|
| 1. 파서 | PyMuPDF vs pdfplumber, 띄어쓰기 복원(kiwi) 유무 | 나머지 | 근거 문장 보존율(근거가 어떤 청크엔가 50% 이상 들어 있는 비율) + 사람 눈 확인 |
| 2. 청킹 | 600 / 1,200 / 2,000자 × 겹침 0 / 150자 (이후 다른 청킹 방식도 후보로 추가 가능) | 기준 임베딩 BGE-M3 | **같은 글자 수 예산**(3,600자) 안의 Recall, nDCG@10 |
| 3. 임베딩 | gemini-embedding-001(768·1,536·3,072), BGE-M3, KURE-v1, Qwen3-Embedding-0.6B, multilingual-e5-large-instruct. (KURE-v2는 문서당 다중 벡터라 pgvector 적재가 어려워 참고 후보로만 실행) | 2단계 1등 | Recall@3·@20, MRR, nDCG@10, 임베딩 속도, 저장 용량 |
| 4. 하이브리드 | 벡터만 vs 벡터 + kiwi BM25 (RRF, k=60) | 3단계 1등 | 위와 같음 |
| 5. 리랭커 | 없음 vs bge-reranker-v2-m3 vs bge-reranker-v2-m3-ko(한국어 추가 학습판), 상위 20개 재정렬 | 4단계 1등 | 위와 같음 + 쿼리당 지연 |
| 6. 운영값 | 쿼리 형태, 최종 k, 유사도 임계값 | 5단계 1등 | 조정용으로 결정, 시험용으로 보고. 임계값은 정답 없는 쿼리의 최고 점수와 정답 쿼리 점수 분포로 정함 |

- **글자 수 예산**: 청크 크기가 다른 구성을 공정하게 비교하려고, 상위 결과를 누적 3,600자가 될 때까지 담아 그 안에 근거가 있는지 본다.
- **신뢰구간**: 쿼리 단위 지표를 1,000회 부트스트랩해 95% 구간을 표시한다. 구간이 겹치면 차이가 없다고 보고 더 단순·저렴한 쪽(작은 차원, 리랭커 없음, 하이브리드 없음)을 고른다.
- **캐시**: 임베딩은 `(모델, 차원, 청킹 설정)`별로 파일 캐시한다.

## 7. 파일 구성

| 경로 | 역할 |
|---|---|
| `rag/eval/requirements.txt` | 실험 전용 의존성(sentence-transformers, torch, kiwipiepy, rank_bm25, pdfplumber, numpy) |
| `rag/eval/metrics.py` | Recall, MRR, nDCG, 근거 매칭, 글자 수 예산, 부트스트랩 (순수 함수) |
| `rag/eval/queries.py` | 시나리오 → 쿼리 생성 |
| `rag/eval/embedders.py` | 후보 모델을 `encode(texts) -> np.ndarray` 형태로 감싸고 캐시 |
| `rag/eval/search.py` | 벡터 검색, BM25, RRF, 리랭크 |
| `rag/eval/pool.py`, `rag/eval/judge.py` | 후보 모으기, Gemini 판정 |
| 검수 아티팩트 | 5.3절 화면 |
| `rag/eval/run.py` | 단계별 실험 실행 → `rag/eval/results/0N_*.md` |
| `rag/eval/plot.py` | 보고서용 그래프 PNG |
| `rag/eval/selected.json` | 최종 설정(하위 프로젝트 3 입력) |
| `tests/rag/eval/` | metrics, 근거 매칭, RRF, pooling 단위 테스트 |

청킹을 실험하려면 수집 파이프라인에서 파서와 청킹 함수를 바꿔 끼울 수 있어야 한다. `rag.ingest`에 `--parser` 인자를 추가하고, 청킹은 기존 `--max-chars`, `--overlap`에 더해 새 방식이 생기면 `--chunker` 인자로 선택한다.

## 9. 위험과 대응

| 위험 | 대응 |
|---|---|
| 쿼리 50개로는 차이가 통계적으로 약함 | 신뢰구간 표시, 차이 없으면 단순한 쪽 선택 |
| pooling 편향(어떤 방식도 못 찾은 정답 누락) | 보고서에 명시, 5.4절 보강 절차 |
| Gemini 판정 오류 | 전수 사람 검수 |
| 로컬 모델 설치 용량(약 2GB)과 속도 | 실험 전용 requirements 분리, 임베딩 캐시 |
| 영문 문서(근감소증, JOMES)와 한국어 쿼리 | 다국어 모델 간 차이가 드러나는 지점으로 결과에 별도 표시 |
| 검수 화면에 지침 원문 일부 포함 | 비공개 아티팩트로 본인만 접근 |
