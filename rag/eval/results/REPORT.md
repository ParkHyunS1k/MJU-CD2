## 1. 결론

| 항목 | 선택 | 근거 요약 |
|---|---|---|
| PDF 파서 | PyMuPDF, 띄어쓰기 복원 없음 | 다른 파서·띄어쓰기 처리와 차이 없음(가장 단순) |
| 전처리 | 머리말·꼬리말·쪽 번호·목차·참고문헌 제거, 소프트 하이픈 복원 | 참고문헌 청크 46개(9%) → 0개 |
| 청킹 | **문단 묶기 1,200자** (문단 경계를 지키며 1,200자까지 쌓음, 겹침 0), **잠정** | 근거 Recall@예산은 "문단 하나씩"보다 낮지만, 맥락이 이어진 청크 3개로 LLM 입력과 인용이 단순하다. 하위 프로젝트 3의 생성 비교로 확정한다 |
| 임베딩 | **BGE-M3** (1,024차원, 로컬) | 7개 모델 중 1등. 무료, API 한도 없음 |
| 하이브리드 (BM25) | 사용 안 함 | 더하면 nDCG 0.791 → 0.748 |
| 리랭커 | 사용 안 함 | 효과 없음(0.792), 쿼리당 약 2.6초 추가 |
| 검색 쿼리 형태 | 키워드형 | 질문형과 차이 없음, 코드로 만들어 단순 |
| k | 3 | 3,600자 예산(청크 길이 중앙값 기준) |
| 유사도 임계값 | 0.6095 (코사인) | 정답 없는 쿼리를 거르되 정답 청크의 90%는 남김 |

**시험용 성능 (k = 3, 임계값 적용, 쿼리 26개):** Recall@3 0.923, nDCG@10 0.649, MRR 0.897. 사람이 검수한 쿼리만 보면 Recall@3 1.000이다.

## 2. 평가 방법

### 2.1 데이터
- **코퍼스:** 학회 진료지침·정부 지침·오픈액세스 논문 16개 문서. 질환과 생활요법 장만 골랐다(`rag/sources.json`).
- **검색 쿼리 54개:** 질환 × 카테고리 시나리오마다 키워드형과 질문형, 인바디 특화 3개, 정답 없는 쿼리 3개. 조정용 25개와 시험용 25개로 나눴다.
- **정답 라벨 922개:** 근거 문장 단위라서 청킹 방식을 바꿔도 그대로 쓸 수 있다.

| 출처 | 개수 | 설명 |
|---|---|---|
| `human` | 163 | 사용자가 직접 검수 (188개 후보) |
| `llm` | 492 | GPT 1차 판정. 사람 검수 188건과 관련 여부가 96% 일치 |
| `llm-gpt` | 267 | 라벨 보강. 청킹 8개 구성 각각의 상위 5개 중 라벨이 없던 청크를 GPT로 판정 |

### 2.2 채점
- 검색된 청크가 같은 문서이고 근거 문장의 50% 이상(공백 제거, 문자 10-gram 기준)을 담고 있으면 그 근거를 찾은 것으로 본다.
- **근거 Recall@예산:** 상위 결과를 3,600자까지 담았을 때(넘치는 마지막 청크는 잘라서) 필요한 근거 문장을 몇 %나 담았는지. 1·2단계의 선택 지표다.
- **nDCG@10:** 정답 청크를 얼마나 위에 올렸는지. 3~5단계의 선택 지표다.
- **선택 규칙:** 쿼리 1,000회 부트스트랩. 1등과의 쿼리별 차이(쌍체)의 95% 구간이 0을 포함하면 "차이 없음"으로 보고 더 단순·저렴한 구성을 고른다.

## 3. 단계별 결과

### 1단계: 파서와 띄어쓰기 (문단 묶기, BGE-M3)

| 구성 | 근거 Recall@예산 | nDCG@10 | 근거 보존율 |
|---|---|---|---|
| **PyMuPDF** | **0.485** | 0.791 | 1.000 |
| PyMuPDF + 띄어쓰기 복원(공백 없는 문서만) | 0.474 | 0.796 | 1.000 |
| PyMuPDF + 띄어쓰기 복원(전체) | 0.480 | 0.794 | 1.000 |
| pdfplumber | 0.459 | 0.740 | 0.956 |
| pdfplumber + 띄어쓰기 복원 | 0.461 | 0.752 | 0.951 |

고혈압 지침은 PDF에 공백이 거의 기록돼 있지 않다(한글 글자당 공백 0.02, 다른 문서 0.2~0.3). 그런데도 띄어쓰기를 복원해도 검색 성능은 달라지지 않았다. 임베딩 모델의 토크나이저가 공백 없는 한국어도 처리하기 때문으로 보인다. 다만 출처 인용문을 사용자에게 보여 줄 때는 복원한 텍스트가 읽기 좋다(하위 프로젝트 4에서 검토).

### 2단계: 청킹 (BGE-M3)

| 구성 | 근거 Recall@예산 [95% 구간] | Recall@예산 | nDCG@10 | 청크 수 |
|---|---|---|---|---|
| 2,000자 / 겹침 0 | 0.408 [0.340, 0.478] | 0.961 | 0.802 | 278 |
| 2,000자 / 겹침 150 | 0.406 [0.335, 0.474] | 0.941 | 0.793 | 292 |
| 1,200자 / 겹침 0 | 0.472 [0.405, 0.543] | 0.980 | 0.775 | 456 |
| **문단 묶기 1,200자** | 0.485 [0.414, 0.557] | 0.980 | 0.791 | 497 |
| 1,200자 / 겹침 150 | 0.465 [0.393, 0.543] | 0.980 | 0.781 | 504 |
| 600자 / 겹침 0 | 0.531 [0.466, 0.595] | 0.980 | 0.742 | 910 |
| 600자 / 겹침 150 | 0.528 [0.458, 0.597] | 0.980 | 0.790 | 1,155 |
| 문단 하나씩 | 0.570 [0.499, 0.638] | 0.980 | 0.708 | 1,825 |

- 규칙대로라면 "문단 하나씩"이 1등이다. 짧은 청크를 예산 안에 많이 담아 서로 다른 근거를 가장 많이 모은다. 쿼리별 쌍체 비교에서 "문단 묶기"는 유의하게 낮다.
- **nDCG@10으로는 청킹을 비교할 수 없다.** nDCG는 근거가 하나라도 든 청크를 정답으로 채점하므로 청크가 길수록 높게 나온다. 근거 3개가 한 절에 있으면 "문단 묶기"는 청크 하나만 1위에 올리면 되지만, "문단 하나씩"은 정답 청크 3개를 모두 위에 올려야 한다. 위 표에서도 청크가 짧을수록 nDCG가 대체로 낮다(2,000자 0.802 → 문단 하나씩 0.708). 그래서 1·2단계는 근거 Recall@예산으로, 청킹이 고정된 3~5단계만 nDCG로 고르도록 설계했다.
- 두 청킹을 각자 3~6단계까지 돌린 운영값(BGE-M3, 키워드형, 시험용 26개):

| 시험용 | k | 넘기는 글자 수(평균 길이 × k) | 근거 Recall@k (임계값 없음) | 근거 Recall@k (임계값 적용) | Recall@k | nDCG@10 |
|---|---|---|---|---|---|---|
| 문단 묶기 | 3 | 약 3,300자 | 0.421 | 0.404 | 0.962 | 0.752 |
| 문단 하나씩 | 13 | 약 4,500자 | 0.638 | 0.599 | 0.962 | 0.675 |

- "문단 하나씩"은 청크 길이가 한쪽으로 치우쳐(중앙값 263자, 평균 346자) 중앙값 기준 k=13이 예산보다 약 4,500자를 넘긴다. 그래서 위 표의 근거 Recall@k 차이는 부풀려져 있다. 같은 3,600자로 비교한 값은 2단계 표의 0.570 대 0.485다.
- 그런데도 **"문단 묶기"를 잠정 선택했다(규칙 밖의 결정).** 지표 우위 때문이 아니라 운영상의 이유다.
  - "문단 하나씩"은 1,825개 중 664개가 200자 미만이다. 제목 한 줄, 목록 한 항목처럼 앞뒤 맥락이 빠진 조각이 많다.
  - LLM에 여러 문서의 조각 13개를 넘기고 인용 13개를 관리해야 한다. "문단 묶기"는 맥락이 이어진 덩어리 3개다.
- 두 지표 모두 리포트가 실제로 나아지는지를 재지는 못한다. **하위 프로젝트 3에서 같은 쿼리로 두 청킹의 리포트를 만들어 정확성과 인용 근거를 비교한 뒤 확정한다.**

- 모든 모델이 청크가 긴 "문단 묶기"에서 점수가 높다. 위에서 설명한 nDCG의 청크 길이 쏠림 때문이므로 두 열은 서로 비교하지 않고 열 안에서만 본다.

### 6단계: 운영값 (조정용으로 정하고 시험용으로 보고)

- **쿼리 형태:** 키워드형 nDCG 0.863, 질문형 0.817로 차이가 없어 키워드형을 골랐다.

- **임계값 0.6095:** 정답 없는 쿼리의 1위 코사인은 0.49, 0.64, 0.56이다. 정답 청크의 90%를 남기는 상한으로 잘랐더니, 정답 없는 쿼리 3개 중 2개가 걸러진다.

## 4. 진행 중 바꾼 결정과 이유

| 날짜 | 변경 | 이유 |
|---|---|---|
| 10-13 | 선택 규칙: 구간 겹침 → **쿼리별 쌍체 차이** | 구간 끝이 닿기만 해도 평균 0.16 낮은 구성을 "차이 없음"으로 골랐다 |
| 10-13 | 글자 수 예산: 넘치는 청크를 빼기 → **잘라서 채움** | 청크 크기마다 실제로 본 글자 수가 달랐다(2,000자 구성은 약 2,300자만 봄) |
| 10-14 | **참고문헌 제거** | 청크의 9%(이상지질혈증은 40%)가 참고문헌 목록이었다 |
| 10-14 | **문단 청커 추가** | 지금 방식은 PDF의 줄 단위로 잘려서 청크의 71%가 문장 중간에서 끝났다 |
| 10-14 | 1·2단계 지표: Recall@예산 → **근거 Recall@예산** | 참고문헌을 뺀 뒤 모든 구성이 0.94~0.98로 차서 변별력이 없어졌다. 결과를 본 뒤 바꿨으므로 두 지표를 함께 싣는다 |
| 10-14 | **라벨 보강** (8개 구성 전부) | 기존 라벨은 옛 청킹에서 모은 후보라 새 청킹에 불리했다 |
| 10-14 | OpenAI 임베딩 후보 추가 (유료) | Gemini 무료 등급 한도 때문에 대안이 필요했다. 결과는 성능 미달 |
| 10-14 | k 규칙: Recall 비율 → **글자 수 예산** | 이전 규칙은 k=1을 골라 근거의 17%만 LLM에 넘겼다 |
| 10-14 | 청킹 잠정 선택: 규칙상 1등("문단 하나씩") 대신 **"문단 묶기"** | 맥락이 이어진 청크와 단순한 LLM 입력·인용. 근거 Recall@예산은 0.485 대 0.570으로 낮다. 처음에는 nDCG가 높다는 이유를 들었으나, nDCG는 긴 청크에 유리해 청킹 비교에 쓸 수 없어 철회했다 |

## 5. 한계

- **시험용 수치는 다소 낙관적이다.** 시험용 쿼리를 빼고 정한 값은 k와 임계값뿐이다. 파서, 청킹, 임베딩은 시험용을 포함한 전체 쿼리로 골랐다(설계 4절).
- **라벨의 82%가 LLM 판정이다.** 사람이 검수한 쿼리는 고혈압·당뇨·이상지질혈증뿐이라 "사람 검수" 열을 함께 봐야 한다.
- **후보 모으기(pooling)의 한계:** 어떤 방식도 찾지 못한 정답은 라벨에 없다. 보강으로 줄였지만 없앤 것은 아니다.
- **쿼리 수가 적다.** 정답 있는 쿼리 51개, 시험용 26개라 구간이 넓다.
- **임계값은 정답 없는 쿼리 3개로 정했다.** 이 3개로 거르는 성능을 보고하므로 검증된 값이 아니다.
- **청킹 선택은 검색 지표만으로 확정하지 않았다.** 근거 Recall@예산은 "문단 하나씩"이 높고, 선택은 운영상의 판단이다.
- **k를 청크 길이 중앙값으로 정한다.** 길이가 치우친 청킹("문단 하나씩")에서는 실제로 넘기는 글자 수가 예산을 넘는다.
- **영문 근거 쿼리(근감소증, JOMES)가 약하다.** 임계값을 적용하면 Recall이 0.857에서 0.714로 떨어진다.

## 6. 남은 일

1. **gemini-embedding-001 (768차원) 비교:** 한도가 풀리면 "문단 묶기"로 3단계에 추가한다. BGE-M3보다 유의하게 높으면 3~6단계를 다시 돌린다.
2. **(선택) Qwen3-Embedding-8B 비교:** GPU(RunPod 등)로 한 번 측정해 성능 상한을 확인한다.
3. **하위 프로젝트 3:** `selected.json`대로 pgvector 적재, 검색 서비스, 리포트 생성 연결. 이때 "문단 묶기"와 "문단 하나씩"(`runs/single/selected.json`, k=13)으로 리포트를 함께 만들어 청킹을 확정한다.
